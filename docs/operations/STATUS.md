### weekly-optimization を止めるときの既知の制約 (記録日: 2026-11-10、今回は直さない)
- 止め方は runner の PID への `kill -TERM` (PR #88)。runner は子孫がすべて終わってから ROLLBACK とロック解放を行う。
- ただし各段階の中のスクリプトが持つ DB のロックは、その孫が終わる前に解放されうる。
  - `ensure-us-adjusted-foundation.ts` は合図を受けるとすぐにロックを外す。直下の npm の終了を待つ版も試したが、
    npm は SIGTERM ですぐ終わるため、隔離試験では孫が終わる 8 秒前にプロセスロックと更新ロックが外れた (効果がないため取り除いた)。
  - 同じ処理は、重複した合図で途中終了しないよう 2 回目以降の合図を無視する。このため、更新ロックを外す処理 (DB への書込み) が
    戻ってこない場合、2 回目の合図では強制終了できない (runner は SIGKILL を使わない)。そうなった場合は、その時点で扱いを検討する。
  - 同じ処理は、合図を受けると自分の更新ロックだけを外して終了し、`source_snapshots` の段階で取る `us_adjusted_source_snapshots` の
    更新ロック (期限 72 時間) は `running` のまま残る (main でも同じ。11/10 の隔離試験で確認)。次に競合するロックを取るときの自動回収
    (所有者の PID と SQLite の Writer を確かめてから `idle` に戻す) か、期限まで残る。11/10 の隔離試験では自動回収されず、次の foundation は
    「already active」で止まった (理由は未確認)。回収されない場合に手で戻すときは、Production の DB 更新として承認を得て行う。
  - `run-ml-learning.ts` は合図を受けるとまずロックを解放し、子に SIGTERM、10 秒後に SIGKILL を送る。
- 運用上の対策: 合図を送る前に、数分以内に他の Writer の予定がないことを確認する。
- 実際に止める操作を使った場合は、その時点で改めて扱いを検討する。
