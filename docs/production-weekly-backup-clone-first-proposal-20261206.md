# 週次 Backup の方式の比較（12/6 に向けた案）

2026-11-15 作成。読み取りの調査だけで書いた案。実装も本番の操作もまだしていない。

## 背景

- 11/15 v2 は、JP と US の同期を両方とも終えた後、`SOURCE_CHANGED_DURING_HOLD` で止まった。
  止めていた時間は 13:01:03〜14:38:14（約 1 時間 37 分）。
- 止めていない Web（:3000）と類似の検索（:3105）は、JP と US の両方の DB を**読み書きできる形で**開いている（`lsof` の fd が `u`、11/15 19:4x に確認）。
- 稼働中のビルド（1724b3b）には、画面を開いたときに JP の DB に書く処理がある：
  - `dashboard_cache`（`lib/queries/dashboard-cache.ts`）
  - `dashboard_earnings_alert_cache`
  - `dashboard_trade_signal_cache`（`lib/queries/dashboard-trade-signals.ts`、`lib/server/two-year-line-search.ts`）
- gateway（:3136）は DB を開いていない。web-health と dev-capacity-monitor は DB に触れない。
- 今の CLI は、同期している市場の DB と WAL だけを毎秒見ている。もう一方の市場は最後の比較まで見ない（JP は 14:00〜14:38、US は 13:01〜14:00）。
  v2 で何が変わったかは記録が残らず、分からない。d933376 で、変わったファイルと値、どちらの同期の後に見つけたかを出すようにした。

## 2 つの方式

**A（今の方式）**
- 16 の Writer を止めたまま、本番の DB から SanDisk の候補へ `sqlite3_rsync` で直接同期する（JP の後に US）。
- 止めている間に本番の DB・WAL が変わったら失敗にする。

**B（先に OWC の上で複製する方式）**
- 16 の Writer を止める。
- JP と US の両方で書き込みの鍵（`BEGIN IMMEDIATE`）を取る。2 つ目が取れなければ、1 つ目をすぐ外して失敗にする。
- 同じ OWC のボリュームの上で、各市場の DB、続いて WAL の順に、APFS の複製を新しい作業用の場所へ作る。場所の例：`StockBoard Development/weekly-backup-staging/<runId>/`。
  - `-shm` は写さない。開くときに作り直される。
  - 複製には `clonefile(2)` を直接呼ぶ。`cp -c` は使わない（理由は下の「確かめること」の 3）。
- 複製と作業用の場所を fsync してから、鍵を外し、Writer を戻す。
- その後、複製を元にして SanDisk の候補へ `sqlite3_rsync` で同期し、確かめる。
- 公開した後（または失敗した後）に、作業用の複製を消す。

## 比べた結果

| 観点 | A（今） | B（先に複製） |
|---|---|---|
| Writer を止める時間 | 約 1.5〜2 時間（v2 は 97 分。JP 約 59 分、US 約 38 分） | **目標は数十秒**（上限は別に定める）。止めると戻すで約 10 秒（v2 の実績：止めて最初の同期まで約 5 秒、戻すのに約 2〜4 秒）、複製で数秒。**本番の DB での複製の時間は未測定**。Writer は 1 つずつ止めて戻し、それぞれに待つ上限があるので、最悪の時間は実績より長い |
| Web・類似の検索 | 止めない。ただし書かれると失敗する（v2） | 止めない。鍵を持つ間、書き込みは待たされる（busy_timeout 5 秒、3 回やり直し）。鍵を持つ時間がこれを超えると、その画面の書き込みは `SQLITE_BUSY` で失敗する |
| SanDisk の容量 | 前回の世代との差の分（v2 では約 46.6 GB） | A と同じ |
| OWC の容量 | 使わない | 作った時はほぼ 0。複製がある間、本番の DB への書き込み・チェックポイント・WAL の書き換え、それに作業用の複製の上での処理の分だけ、共有が外れて増える。db-maintenance は VACUUM をしない（`scripts/maintenance-db.ts:4`、チェックポイントは :305）ので、1 日なら数 GB の見込み。ただし、これは見込みで、上限の保証ではない。OWC の空きは 2.19 TB。**OWC は本番の DB の置き場なので、満杯は本番に響く**。空きの下限、増える量の上限、見張る間隔、残った作業用の複製の片づけ方を計画に入れる |
| 保証の強さ | 止めている間に何も変わらなかったときだけ、JP と US が同じ時点のものになる。変わると失敗する（安全側だが、再実行が要る） | JP と US の両方が、**両方の鍵を持った時点の、確定した取引だけの状態**になる。その後の Web の書き込みに左右されない。同期の元が動かないので、同期は長い Writer の停止に縛られない。ただし、計画の終わりの時刻と、確かめの時間の上限は今までどおりある |
| 両方の方式に共通の限界 | JP と US にまたがる処理や、いくつかの取引に分かれた処理の途中の状態は、そのまま写る（runbook の既存の但し書きのとおり） | 同じ |
| 弱いところ | Web の書き込みが 1 回でもあると失敗する。止める時間が長い | 鍵と複製の正しさの説明に頼る（下の「確かめること」）。本番の DB に鍵を取る接続を開く。OWC に一時ファイルを作り、消す |
| コードの変更量（見込み） | 0（今のまま） | **合計 約 +500〜700 行**（初めの見込みの +300 は少なすぎた）。内訳：鍵の取得と解放（異常時を含む）、`clonefile(2)` の直接の呼び出し、fsync、OWC の容量の見張り、作業用の複製の片づけ、計画の項目、テスト（同時の書き手とチェックポイント、WAL が無い・0 バイト、鍵が取れない、容量の下限）、runbook。元の DB の監視は、更新時刻の監視だけを外す。ファイルの番号、ボリューム、WAL の同一性、知らない Writer の見張りは残す |
| 本番での事前確認 | 済み（v1・v2） | OWC の上で複製の時間と容量を測るリハーサルが要る（承認が要る） |

**参考：A のまま直す案**
- A1：Web と類似の検索も 1.5〜2 時間止める。変更は小さいが、画面が長く止まる。
- A2：キャッシュ表への書き込みは許す。JP と US が同じ時点という保証が弱くなる。変わったことに気づけない。
- どちらも勧めない。

## B で確かめること（実装の前に、テストで）

1. **鍵を持っている間の、他の接続のチェックポイント**
   - 鍵を持っている間でも、他の接続の受け身のチェックポイント（PASSIVE）は、WAL の中身を DB に書くことがある。
   - ただし、WAL を先頭に戻したり書き足したりできるのは、鍵を持つ書き手だけ。だから WAL の中身は消えない。`-shm` を写さなければ、開くときに WAL を全部当て直すので、確定した状態に戻る（Codex も、条件付きで正しいと判断）。
   - 条件：
     - 両方の鍵を、最初の複製の前から最後の複製の後まで持つ。
     - 鍵を持つ接続は、何も書かない（チェックポイントもしない）。
     - 作業用の場所は新しく作る（古い `-shm` を置かない）。
     - 複製の前後で、WAL のファイルの番号、大きさ、ヘッダーと salt を比べる。DB の更新時刻はチェックポイントで変わりうるので、条件にしない。
   - 複製の途中で書き手とチェックポイントを同時に起こす試験で、複製を開いた結果が、鍵を取った時点の確定した状態と一致することを確かめる。
2. **鍵を取れないとき**
   - 長い取引が鍵を持っていて取れない場合は、待つ上限を決めて、失敗として戻す（Writer は戻す）。
3. **`cp -c` は、複製ができないと、黙って普通のコピーにする**
   - `man cp` に書いてあり、確かめた。普通のコピーになると、数秒では終わらず、容量も 550 GB ずつ使い、一度に写した状態という前提も崩れる。
   - Node の `COPYFILE_FICLONE_FORCE` は、この Mac では `ENOSYS` で使えない（試した）。
   - `clonefile(2)` を直接呼ぶと、同じボリュームでは 1 ミリ秒未満で成功し、別のボリュームでは「Cross-device link」で失敗した。作業用の場所でだけ試し、SanDisk には何も作られていない。B ではこれを使う。
   - 開いた元のファイルと複製するファイルが同じものであることも、ファイルの番号で確かめる。
   - 今の CLI が SanDisk の上で前回の世代を複製するところも `cp -c` を使っている。ただし、こちらは普通のコピーになっても、容量の上限と時間の上限で止まる。直すかどうかは別に決める。
4. **複製の時間**
   - 本番の DB は書き換えが多く、細かく分かれている。そのため APFS の複製は、SanDisk の上（v2 では 2 つで約 1 秒）より遅い可能性がある。
   - リハーサルで測り、鍵を持つ時間の上限を決める。
5. **作業用の複製を必ず消すこと**
   - 失敗や停電の後は手で消す手順を runbook に書く。OWC の空きに下限を設け、下回ったら同期を止めて複製を消す。
6. **確かめ方**
   - 複製を元にするので、候補が複製と同じであることを確かめられる。
   - 例：複製の WAL を、複製の上だけでチェックポイントしてから、両方の SHA-256 を比べる。時間はかかる。

## 勧め

**B を 12/6 の案にすることを勧める。**
- 止める時間が約 100 分から 1 分未満に減る。
- Web の書き込みで失敗する、という今回の型の失敗がなくなる。
- 保証も強くなる。

ただし、本番の DB に鍵を取ることと、OWC に一時ファイルを作ることについて、承認が要る。コードの量は A より大きく増える（約 +500〜700 行）。

**進め方の案**
1. 11/16〜11/22：実装。テストに上の 1〜3 と 5 を入れる。Codex のレビュー。
2. 11/22 か 11/29（日）：OWC での短いリハーサル（承認の後）。複製の時間、鍵を持つ時間、容量を測り、すぐ消す。SanDisk への同期はしない。
3. 12/6：本番の実行（承認の後）。

A を続ける場合は、A1 か A2 を選ぶ必要がある。今のままでは、Web が書くたびに同じ失敗が起きる。

## SanDisk の容量（12/6 に向けて）

- 今の空きは 849,139,703,808 バイト。runbook の (2) で、空きが 850 GB 以上あることを確かめる（予備 150 GB ＋ 増える上限 700 GB）が、その 850 GB に足りない。
- v1 のコピーは、前回の世代の APFS の複製で、何も書かれていない。そのため**消しても空きは約 0.06 MB しか増えない**（v1 のログで、空きの減りは約 16 KB）。v1 を消すだけでは足りない。
- v2 のコピー（暫定の控え）が約 46.6 GB を使っている。これは CLI と同じ、ボリュームの空きの差で測った値（895,736,213,504 → 849,139,552,256 バイト）。
- 案：12/6 の計画で、増える上限を 700 GB から 650 GB に下げる。
  - このとき、要る空きは 800 GB になる。今の空きなら約 49 GB の余裕がある。
  - これは要る量の予測ではなく、安全側の上限を下げる変更である。
  - 12/6 も前回の世代は 10/22・10/23 のまま。増える量は、そこからの差（11/15 の時点で約 47 GB）に 3 週分が加わる。
  - 計画の値の変更なので、承認が要る。
